# C naming conventions

Status: adopted with Phase 3 on 2026-07-20, recording the conventions the
Phase 2 engine shipped with. Applies to every C symbol in
`packages/tex-core` — engine, tests, fuzz targets, and CLI. The public
facade surface (`include/tex_core.h` + the export header) goes through a
naming freeze review before the 1.0.0 release. Modeled on markdown-core's
`c-naming.md`; responsibilities are copied, names are not.

## Rules

1. **Two prefixes.** Public symbols — everything declared in
   `include/tex_core.h`, plus the version macros — are spelled
   `tex_core_…`/`TEX_CORE_…`. Internal symbols that cross translation
   units are spelled `txc_…`/`TXC_…`, including test-harness and
   fuzz-target helpers. No third family, and no unprefixed cross-TU
   symbol: leading-underscore names are reserved identifiers, and
   unprefixed names leak into consumer link namespaces when
   static-linking.
   - This is a deliberate divergence from markdown-core, which spells
     internals with the full public prefix. tex-core's engine builds with
     hidden visibility, so `txc_` symbols never escape the shared
     library; the static archive does expose them, which the short
     distinctive prefix keeps collision-safe. Revisit at the 1.0.0
     naming freeze.
2. **Subject first.** Functions are `<prefix>_<subject>_<verb>[_<object>]`,
   where the subject is the type the function operates on or produces:
   `tex_core_document_compile`, `tex_core_render_tree_dump`,
   `tex_core_options_init`, `txc_scanner_init`, `txc_metric_find`.
   Attribute and navigation accessors are bare nouns
   (`tex_core_node_child`, `tex_core_node_range`, `tex_core_node_frame`).
3. **`get_` only under occupation.** An accessor takes `get_` exactly when
   its bare name is occupied by a type: `tex_core_node_get_kind` exists
   because `tex_core_node_kind` is the enum type. Nothing else takes
   `get_`; do not extend the cluster without the same collision.
4. **One-word module verbs.** Each engine module exposes its entry point
   as a single verb on the module's subject: `txc_scan`, `txc_parse`,
   `txc_layout`, `txc_dump`, `txc_fail`. Prefer a precise single word to
   a compound; compounds are for real two-part meanings
   (`txc_scaled_format`, `txc_utf8_next`).
5. **Files are feature-named single words** under `core/`: `token.c`,
   `parse.c`, `layout.c`, `dump.c`, `scaled.c`, `metrics.c`, `memory.c`,
   `error.c`, `utf8.c`. A file is named for the feature it implements,
   not its role in a pattern (no `utils`, `helpers`, `common`).
6. **Types and constants** follow the prefix rule: types are lowercase
   (`tex_core_render_tree`, `txc_scanner`), enum constants and macros are
   upper snake (`TEX_CORE_NODE_GLYPH`, `TXC_EM_SP`). Enum constant names
   put the type's noun before the value (`TEX_CORE_STYLE_UPRIGHT`).
7. **File-local statics** are free-form; they carry no prefix obligation
   because they have no linkage. In practice they keep the `txc_` spelling
   for greppability.

## Aesthetics

New coined identifiers follow the repository's naming taste: neutral
connotation, no cuteness, and — for user-facing coinages — a preference
for glyphs without descenders. Propose candidate names in review rather
than defending a rejected one.

## Non-goals

Historical documents keep the names that were current when written.
Generated tables (`metrics.inc`) are regenerated by their maintenance
script, never hand-edited; the generator owns their internal naming.
